# MathGuard-Offline

> 一个**纯离线**的 LaTeX 结构与公式数值校验工具，专为严谨的数学研究者设计。
> 我们拒绝用大模型做算术，只提供**绝对确定**的四态报告，杜绝任何假阳性幻觉。

## 一句话

把你论文的 `.tex` 丢进去，它会告诉你三件事：

1. **哪些标签是孤儿**（定义了却从没人引用）
2. **哪些引用是断的**（引用了不存在的标签）
3. **哪些数字算错了**（`2+2=5` 这种）

而且，**它不会骗你**——读不懂的公式会老实说"我没法判定"，绝不冒充"通过"。

---

## 核心设计：四态报告

这是本工具与所有"AI 科研助手"的根本区别——**工具不懂时不装懂**。

| 标记 | 状态 | 含义 | 你该怎么做 |
|:---:|---|---|---|
| `[✓]` | **已验证通过** | 确实做过一次确定的数字判定，且成立 | 放心 |
| `[✗]` | **验证失败** | 数字关系**确定**不成立。这是唯一可以断言"错"的状态 | **必须修** |
| `[≈]` | **仅可解析** | 能读懂（语法正确），但没有任何可判定的数字关系：表格数据、纯符号等式、同余式 | 工具没发现问题**不代表正确**，需人工判断 |
| `[–]` | **无法验证** | 超出当前能力（矩阵、多层求和、深层嵌套等），已安全跳过 | 同上，需人工判断 |

### 为什么要有 `[≈]`

早期版本曾把"能解析"当成"验证通过"，结果一篇论文报出 232 条"通过"，其中 30 条只是表格里的 `64`、`(12,4)` 这类数据——**毫无证明价值**。

现在的原则是：**只有真的做过判定，才配叫"通过"**。实测某篇论文 191 条公式里，真正被验证的只有个位数，其余都如实归入 `[≈]`。

### 一个真实案例

开发中曾出现如下 Bug：Python 3.13 起 `ast.literal_eval` 不再接受二元运算，`2+2` 抛异常被吞掉，判定环节静默跳过，最后返回了 `ok`——**`2 + 2 = 5` 被判为通过**。

这类"异常静默（silent failure）"是最危险的：工具看似正常，结论却是假的。现在改为白名单遍历求值，并有专门的回归测试锁定此问题。

## 快速开始

### 方式一：直接下 exe（无需 Python）

1. 下载 [MathGuard-Windows-x64.zip](https://github.com/USERNAME/MathGuard-Offline/releases/latest)（37.8 MB）
2. 解压到任意位置
3. 打开 cmd，cd 到该文件夹，运行：

```cmd
math_guard.exe 你的论文.tex
```

先自测一下：

```cmd
math_guard.exe example.tex
```

### 方式二：从源码跑

```bash
pip install sympy
python math_guard.py 你的论文.tex
```

可选增强（装了会做交叉校验，不装也能用）：

```bash
pip install latexnav parsub
```

## 使用

```bash
python math_guard.py paper.tex              # 极速体检：只报致命错误与算错的公式
python math_guard.py paper.tex --lint       # 导师强迫症模式：额外查公式末尾缺标点
python math_guard.py paper.tex -v           # 列出每条被跳过/仅可解析的公式及原因
python math_guard.py paper.tex --no-color   # 关颜色（重定向到文件时用）
python math_guard.py --demo                 # 生成含预设错误的示例并体检
```

### 批量检查（快 5-6 倍）

单篇启动约 1.3 秒，其中 ~0.7 秒是加载 sympy 的固定成本。**要查多个文件或整个目录时，用 `--batch`**：

```bash
python math_guard.py --batch 论文目录/ -q          # 一条命令查整个目录，每篇一行摘要
python math_guard.py --batch a.tex b.tex c.tex     # 指定多个文件
python math_guard.py --batch 目录/ -q --lint       # 批处理 + 标点检查
```

实测对比（21 个文件）：

| 方式 | 耗时 | 平均 |
|---|---|---|
| 逐篇调用 | 27.4s | 1.30s/篇 |
| `--batch` | **4.6s** | **0.22s/篇** |

251 个文件批处理只需 **50 秒**。判定结果与逐篇调用**完全一致**。

### 退出码

| 码 | 含义 |
|:---:|---|
| `0` | 干净 |
| `1` | **仅结构问题**（孤儿标签 / 未定义引用）——排版卫生 |
| `3` | **存在验证失败**（数字关系确定不成立）——内容错误，最严重 |
| `2` | 用法错误 |

分级的原因：CI 应当能区分"论文里公式算错了"和"有个标签没人引用"。

```bash
# 只在数学确实算错时才让流水线失败
python math_guard.py paper.tex
case $? in
  0) echo "OK" ;;
  1) echo "仅有排版问题" ;;
  3) echo "数学错误，必须修" ; exit 1 ;;
esac
```

## 特性

- **完全离线**：封死全部 socket 后仍可完整运行。无网络请求、无遥测、无 API key。
- **零假阳性优先**：宁可少报，不可错报。实测 251 份真实文档零崩溃，6 类历史误报全部修复并锁定为回归用例。
- **严格四态**：从不把"读懂了"伪装成"验证过了"。
- **内建宏库**：277 条 LaTeX 数学命令（`latex_macros.py`），离线、零依赖。
- **永不崩溃**：空文件、二进制乱码、6000 位大数、3000 层括号、GBK 编码等恶劣输入均安全退出。

| Big5 | ✅ | |

| 多文件（`\input`） | ✅ | 指向主文件，自动递归展开，报告显示真实 `文件:行号` |

### 为什么只接受 `.tex`

| 输入 | 公式能否还原 | 结构检查 | 结论 |
|---|:---:|:---:|---|
| `.tex` 源码 | ✅ | ✅ | **唯一可靠输入** |
| `.pdf` | ❌ 拆成排版碎片 | ❌ | 拒绝 |
| `.docx`（pandoc 转） | ⚠️ 仅 Office Math 公式 | ❌ 引用变纯文本 | 只能看公式 |

**PDF 实测**：把 PDF 文字层直接送进工具 → 提取 **0 条公式** → 报告"体检通过"。这是最坏的结果，所以工具会明确拒绝。

**Word 部分可用**：

```bash
pandoc 论文.docx -t latex -o 论文.tex
python math_guard.py 论文.tex    # 公式能查，结构检查不可信
```

## 检查模块

| 模块 | 内容 | 级别 | 默认 |
|---|---|---|---|
| **结构** | 孤儿标签 / 未定义引用 / 重复标签 | `[✗]` | ✅ 开 |
| **语法 · 环境配对** | `\begin`/`\end` 缺失、名字不符、嵌套错序 | `[✗]` 编译失败 | ✅ 开 |
| **语法 · 括号配对** | `{}` 与 `\left...\right` 用栈扫描 | `[✗]` 编译失败 | ✅ 开 |
| **语法 · 空参数** | `\frac{a}{}`、`\binom{}{}`、`\frac{\cdot}{}` | `[✗]` 渲染缺陷 | ✅ 开 |
| **公式验证** | 数字关系自洽性（四态） | `[✓]/[✗]/[≈]/[–]` | ✅ 开 |
| **排版 · 公式标点** | 行间公式末尾缺 `,` 或 `.` | `[!]` 警告 | ⚠️ 需 `--lint` |

实测数据（259 份真实文档）：

- 语法错误：**6 个文件**（环境/括号），逐条核实**全部是真错误**
  （如 `\end{umerate}` 少个 n、`\binom{2t}{t}` 少个 `}`、`itemize` 未闭合）
- 空参数错误：去重后 26 处，逐条核实**全部是真问题**
- 标点警告：`--lint` 模式下 93 个文件 / 309 条

## 实战战绩

> **在真实数论论文（Apéry midpoint congruences，已定稿 55 页 PDF）的测试中，
> MathGuard 成功拦截了一处已经印进 PDF 的 `\frac{}{}` 空分母排版错误，
> 以及 4 处空占位符错误。**
> 我们只用真论文做测试。

### 这处错误长什么样

该论文第 38 页公式 (7.16)，源码（`sec7_Sn.tex:145`）：

```latex
{}_{2}F_{1}\Bigl(\hf,\hf;1;4e^{x}(1-e^{x})\Bigr)
  =(2e^{x}-1)^{-1}{}_{2}F_{1}\Bigl(\hf,\hf;1;\frac{-(e^{-x}-1)^{2}}{}\Bigr)
                                                  ^^^^^^^^^^^^^^^^^^^^^^^^
                                                  分母是空的 {}
```

**LaTeX 编译不报错**，PDF 里渲染成一道空横线——肉眼要盯着看才发现。
而公式下方紧接着的文字写着分母应为 `(e^{x}-1)^{2}`，说明确实是漏写了。

同一篇论文里还有：

| 位置 | 源码 | 问题 |
|---|---|---|
| `sec5_exp.tex:197` | `\binom{}{}=0` | 上标下标都是空的 |
| `sec9_tower.tex:213` | `\frac{\cdot}{}` | 分子分母都是占位符 |
| `zagier_d_report.tex:481` | `\int\frac{\cdot}{1-x}` | 分子是占位符 |
| `zagier_d_report.tex:521` | `\frac{\ldots}{m-a}` | 待填草稿 |

**这 5 个片段已全部写入自测用例**，以后每次改动都必须验证仍然能抓到。

## 已知边界

本工具的原则是 **宁可少报，绝不误报**。以下情况明确不做，并附上实测理由。

### 不做：验证定理/证明的正确性

`a²+b²=c²` 写成 `a²+b³=c²`，**工具分不出来**——两者都会归入 `[≈] 仅可解析`。

这类推导错误需要形式化证明器（Lean 4），不在本工具的范围内。**工具只做确定性校验，不做数学推理。**

### 不做：「未定义符号」检查（模块四）

原计划检查"某个单字母变量全文只出现一次且未定义"。**实测数据否定了这个方案**：

在两篇真实论文上跑（`an_midpoint_详解.tex` 191 条公式、`Wn层提升定理.tex` 464 条公式），
"全文只出现一次的单字母"共找到 **3 个**：

| 符号 | 实际含义 | 判定 |
|---|---|---|
| `e` | 自然常数 | ❌ 误报 |
| `H` | 正文中有「乘 $H$ 修正」 | ❌ 误报 |
| `M` | 正文中写作 `$\mathcal M$` | ❌ 误报 |

**3 个全是误报，命中率 0%。**

原因是数学论文的符号体系天然模糊：`p` 默认素数、`α/β` 默认参数、`k/n/i/j/m` 是万能下标。
任何基于"出现频次"的规则都会淹没在误报里。**与其报警扰民，不如不报。**

### 不做：中英混排空格检查

不同期刊、不同模板的风格差异极大（ctex 与普通 article 的默认行为不同），无法定义"正确"。这类检查只会制造噪音。

### 默认关闭：公式标点检查（模块六）

检查行间公式末尾是否缺少 `,` 或 `.`。**默认不启用，需加 `--lint`**。

原因：实测 259 份文档产生 **309 条警告**（93 个文件命中）。虽然抽样核实大部分是真缺失，
但对"只想确认公式对不对"的人来说，格式警告会淹没真正的问题。

```bash
python math_guard.py paper.tex          # 极速体检：只报会导致编译失败的致命错误
python math_guard.py paper.tex --lint   # 导师强迫症模式：连缺标点也查
```

### 刻意不报错的写法

以下"看着像问题"但实际合法，工具不会报错：

- **勒让德/雅可比符号** `$\left(\frac{5}{11}\right)=1$` —— 不是除法
- **导数记号** `${}'=d/d\tau$` —— 是定义说明
- **章节标题里的记号** —— 用于指代，不是断言
- **邻近文字提到"取模"** —— 等号可能是模意义写法
- **多行公式的续行**：`$\displaystyle\Sigma_4(m)\equiv$`（以关系符结尾）
- **嵌在中文句中的符号代用**：`题设常数 $=2\times10^{-4}$`、`ESS$>1000$`
- **中文标签不等式**：`$\text{教育价值} \ge P_{75}$`
- **`\bigl`/`\bigr` 配对**：`\bigr|_{t=x}` 是合法的求值记号

### 不做：PDF / Word 直接解析

PDF 里的公式是排版碎片，Word 的交叉引用是纯文本。强行解析会得到错误数据。详见上一节。
